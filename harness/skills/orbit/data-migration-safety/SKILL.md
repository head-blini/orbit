# data-migration-safety

대상은 **이번 변경분의 스키마·마이그레이션·쿼리**다. 결과는 DATA.md에 쓴다.

## 먼저

- 운영 DB에는 접근하지 않는다. 읽기도, 마이그레이션 실행도 하지 않는다. 시험은 로컬·테스트 DB에서만 한다.
- 마이그레이션 **실행**은 사람 승인이 필요하다(운영 대상이면 무조건). 계획과 파일을 만드는 데서 멈추고 Lead에게 승인을 요청한다.

## 점검

1. **되돌리기**: down 마이그레이션이나 롤백 절차가 있는가. 되돌릴 수 없으면(컬럼 삭제, 타입 축소, 데이터 변환) 그렇다고 명시하고 백업 방법을 적는다.
2. **파괴적 변경**: 컬럼·테이블 삭제, 이름 변경, NOT NULL 추가, 타입 변경은 한 번에 하지 않고 "추가 → 데이터 이전 → 코드 전환 → 삭제" 단계로 나눌 수 있는지 본다.
3. **잠금·대용량**: 큰 테이블에 인덱스 추가·컬럼 추가·전체 갱신이 있으면 잠금 시간과 배치 처리 여부를 적는다.
4. **기본값·기존 행**: 새 NOT NULL 컬럼에 기본값이 있는가. 기존 행이 제약을 어기지 않는가.
5. **무결성**: 외래 키, 유니크, 인덱스가 의도와 맞는가. 쿼리가 새 인덱스를 쓰는가.
6. **코드와의 순서**: 배포 중 옛 코드와 새 스키마(또는 반대)가 함께 돌아도 깨지지 않는가.
7. **시드·백업**: 시드 데이터가 비밀값이나 실제 개인정보를 담지 않는가. 실행 전 백업이 있는가.

## DATA.md 형식

스키마 변경 요약 · 마이그레이션 계획(순서) · 롤백 방법 · 위험(잠금·데이터 손실) · 실행 승인 필요 여부. 확인하지 못한 항목은 못 했다고 쓴다.
