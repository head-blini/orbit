# QA 화면 자동화가 전면 앱으로 키 입력을 흘린 사고

## 증상
QA가 osascript로 앱에 키를 보냈는데 Orbit이 아닌 전면의 다른 앱(사용자가 쓰던 창)에 입력이 들어갔다.

## 원인
System Events의 키 입력은 대상 창이 아니라 그 순간 전면 앱으로 간다. 앱 실행·창 전환이 늦거나 사용자가 창을 바꾸면 전면 앱이 달라진다.

## 해결
키를 보내기 전에 전면 앱이 Orbit인지 확인하고, 아니면 보내지 않고 중단한다.

## 다음에 미리 할 것
- GUI 자동화 키 입력마다 직전에 전면 앱 이름을 확인하는 단계를 둔다.
- 가능하면 키 입력 대신 앱 안에서 검증할 수 있는 경로(테스트, 프론트 브라우저 확인)를 먼저 쓴다.
- 확인이 어려운 항목은 사용자 확인 대기로 남긴다.

## 서브에이전트에 브라우저 도구가 없을 때 (run 20261120-ui-attention)
- 증상: qa 서브에이전트에 브라우저·화면 도구가 없어 화면 동작(⌘J 이동, 스크롤, 묶음 펼침)을 직접 볼 수 없었다.
- 해결: 자동 테스트와 빌드 출력은 VERIFY에 붙이고, 화면 항목은 사용자가 실제 앱을 띄워 보는 실기 점검(USER_CHECK)으로 VERIFY를 마쳤다. 점검에서 나온 문제(스크롤이 테두리를 덮음)는 debugger가 headless Chromium 픽셀 측정으로 재현·수정했다.
- 다음에 미리 할 것: 화면 변경 run은 시작 때 qa의 브라우저 도구 유무를 확인하고, 없으면 사용자 점검 절차(띄우는 명령·볼 것·회신 형식)를 VERIFY 전에 준비한다.

## GUI 실기 점검 수단 (run 20261120-flow-panel)
- 증상: 화면 변경을 qa가 볼 방법이 마땅치 않았다.
- 해결: 프론트는 headless Chromium에서 Tauri IPC 목(`window.__TAURI_INTERNALS__`)을 심어 시나리오를 구동하고 스크린샷을 찍는다. 실제 앱은 `screencapture -l <창번호>`로 첫 화면을 찍는다. 손쉬운 사용 권한 오류 -1719가 나면 클릭·키 입력은 불가능하다.
- 다음에 미리 할 것: -1719가 나면 세션 선택 뒤 화면은 미확인으로 두고, 사용자가 위험을 수용한 기록(USER_ACCEPT)을 남긴다.
