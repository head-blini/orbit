## 문제

사용자가 실제로 얻으려는 결과(한 문장):
**훅이 없던 세션, Orbit이 꺼져 있던 동안의 세션, 그리고 훅으로는 오지 않는 "새 세션 시작"까지 Orbit 화면에 세션 하나당 한 줄로 모이고, 같은 도구 호출이 훅과 로그 양쪽에서 와도 한 번만 보인다.**

정말 풀어야 할 문제는 "파일 감시기를 다는 것"이 아니라 **두 번째 데이터 통로(로그)를 첫 번째(훅)와 같은 세션 모델로 합치는 것**이다. ②는 훅 이벤트를 해석 없이 emit만 하고, 세션이라는 단위도 중복 제거도 없다. ④(그래프·타임라인)는 "세션 → 이벤트" 모델을 입력으로 받으므로, 이번 run이 그 모델의 최소형을 처음 만든다. 중요한 것은 세 가지다.
1. 로그 형식이 바뀌어도(공식 스키마 없음, RESEARCH 질문 1) 감시가 죽지 않는다. release 빌드는 `panic = "abort"`라 파서 panic 한 번이 앱 전체 종료다.
2. 같은 사건은 한 번만 보인다(키: 세션 ID + `tool_use_id` + 종류, 없으면 로그 줄 `uuid`).
3. 감시가 Claude Code를 막지 않는다: 읽기 전용, 파일 핸들을 오래 쥐지 않고, 쓰기·삭제·이름 변경을 방해하지 않는다.

## 누구를 위한 것

- 1차: 터미널에서 Claude Code를 쓰며 옆에 Orbit을 켜 두는 개발자 본인(도그푸딩 사용자). 특히 Orbit을 나중에 켰거나 훅을 아직 설치하지 않은 경우.
- 2차: 마일스톤 ④의 팀. 이번 run이 만드는 세션·이벤트 형태(emit 이름과 payload)가 그들의 입력이다.

## 범위 안 (가장 작은 버전)

1. **로그 루트 결정**
   - 기본: `%USERPROFILE%\.claude\projects`(크로스플랫폼은 홈 기준). `CLAUDE_CONFIG_DIR` 처리는 열린 질문 5.
   - 개발 빌드 전용(`#[cfg(debug_assertions)]`) 환경변수 하나로 임시 폴더를 가리킨다(②의 `ORBIT_CLAUDE_SETTINGS`와 같은 방식, 이름은 Architect가 정함). 릴리스 빌드에서는 이 덮어쓰기가 컴파일되지 않는다.
2. **파일 선별**: `projects/<slug>/<uuid>.jsonl`만 세션 로그로 본다. `.orphaned-…jsonl`, `.jsonl.superseded-…`, `tool-results/`, `mcp-tasks/`, `*.meta.json`, `*.prefix.json`은 무시. `subagents/agent-*.jsonl`은 열린 질문 3.
3. **이어 읽기**
   - 파일마다 (경로, 읽은 바이트 위치)를 기억하고 새로 붙은 부분만 읽는다. 완결된 줄(`\n`)까지만 처리, 반쪽 줄은 다음 회차로.
   - 크기가 기억한 위치보다 작아지면 처음부터 다시 읽는다(중복은 2번 키로 걸러짐).
   - 파일이 사라지면 오류가 아니라 "로그 없음"으로 처리. 열기 실패(공유 위반 등)는 조용히 다음 회차에 재시도.
   - 읽을 때마다 열고 닫는다. 공유 모드는 Rust 기본값(READ|WRITE|DELETE) 그대로.
   - 감시 방식(폴링/notify)은 열린 질문 1.
4. **파서 (죽지 않기)**
   - 줄을 `serde_json::Value`로 받고 `type`은 문자열로 본다. 모르는 type·키는 무시, JSON이 깨진 줄은 건너뛰고 위치는 전진.
   - 줄 길이 상한을 넘는 줄은 파싱하지 않고 건너뛴다(값은 열린 질문 6). `\n` 없이 상한을 넘게 자라는 꼬리도 같은 처리.
   - 파서·감시 코드에 `unwrap`/인덱싱 panic 경로를 두지 않는다.
   - 뽑는 값은 화면 확인에 필요한 최소: 세션 ID(파일명 stem, 줄의 `sessionId`), `cwd`, `timestamp`, 줄 `uuid`, `message.content[]`의 `tool_use`(`id`, `name`) / `tool_result`(`tool_use_id`). 나머지는 원본 그대로 두거나 버린다.
5. **세션 모델 + 훅과 합치기 + 중복 제거 (메모리)**
   - 세션 ID로 upsert. 새 `<uuid>.jsonl`이 보이면(또는 첫 줄을 읽으면) 세션이 생긴다 = SessionStart의 대체 신호. 시작 시각은 첫 줄의 `timestamp`.
   - ②의 훅 이벤트도 같은 모델에 들어간다(훅 페이로드의 `session_id`, `tool_use_id`).
   - 중복 키: `(세션 ID, tool_use_id, 종류)` — 종류는 {호출 시작: PreToolUse ↔ `tool_use`, 결과: PostToolUse·PostToolUseFailure ↔ `tool_result`}. `tool_use_id`가 없는 로그 줄은 `(세션 ID, uuid)`. 키가 없는 것(훅의 UserPromptSubmit·Stop 등, uuid 없는 로그 줄)은 중복 제거 대상이 아니다(열린 질문 7).
   - 합치는 위치(Rust/프론트)와 저장 여부는 열린 질문 2·4.
6. **시작 시 과거 기록 읽기**: 앱 시작 시 기존 로그를 읽어 세션을 복원한다(UI 스레드가 아닌 곳에서, emit은 묶어서). 얼마나 거슬러 읽을지는 열린 질문 4.
7. **최소 화면 (디자인은 ④)**: 기존 화면 안에 다음만.
   - 감시 중인 로그 폴더 경로 한 줄(또는 실패 사유).
   - 세션 목록: 세션 ID 앞부분 · `cwd` · 마지막 활동 시각 · 출처(훅/로그/둘 다).
   - 세션을 고르면(또는 세션별로 펼쳐서) 타임라인 최소 표시: 시각 순으로 도구 이름과 단계(호출/결과), 각 항목의 출처.
   - 로그·페이로드에서 온 문자열은 텍스트로만 렌더(`dangerouslySetInnerHTML` 금지). `cwd`는 표시만, 경로·명령으로 쓰지 않는다.
   - 로그 줄의 내용(프롬프트·도구 입출력)은 콘솔·파일 로그에 찍지 않는다.
8. **자동 테스트**: 임시 폴더(기존 테스트의 `temp_dir()+pid+카운터` 패턴)에 줄을 덧붙이는 단위 테스트(아래 성공 기준 1).

자동 테스트
1. `src-tauri/`에서 `cargo test`가 0으로 끝난다. 테스트에 최소한 다음이 있다(모두 임시 폴더).

12. 앱을 실행·종료하는 동안 임시 폴더의 JSONL 파일 내용이 바뀌지 않는다(실행 전후 해시 비교). Orbit은 로그를 쓰지 않는다.

14. 사용자가 환경변수 없이 앱을 띄워 실제 `~/.claude/projects`의 세션이 목록에 복원되는 것, 그리고 터미널에서 새 Claude Code 세션을 열고 도구를 쓰면 그 세션이 나타나고 훅(설치된 경우)과 로그의 같은 도구 호출이 한 번만 보이는 것을 본다. 이때 훅 `tool_use_id`와 로그 `tool_use.id`가 실제로 같은 값인지(RESEARCH 미확인 항목)가 함께 확인된다 — 다르면 같은 호출이 두 번 보인다.

## 열린 질문 (사용자가 정한다)

1. **감시 방식: std 폴링 vs `notify` 크레이트**
   - (A) std 폴링: 1초마다 파일 목록·크기를 보고 커진 파일만 읽는다. 의존성 0, 테스트 쉬움.
     최악: 표시 지연 최대 약 1초 + 처리 시간. 로그 파일이 수천 개로 늘면 매 주기 stat 비용이 커진다(이 PC는 100여 개라 가벼움으로 추정, 측정 안 함). 그때는 주기 늘리기나 최근 파일만 보기가 필요.
   - (B) `notify` 8.x: 이벤트로 깨우고, 그래도 주기적 전체 보정 스캔을 함께 둔다(RESEARCH: Windows 버퍼 넘침 시 이벤트 유실을 알리지 않음, 크기 변경 통지가 지연·병합됨).
     최악: 새 의존성(전이 의존성 목록·8.x 라이선스 미확인)이 붙고, 보정 스캔 때문에 (A)의 코드를 어차피 포함한다. 보정 스캔을 빼먹으면 줄을 조용히 놓친다. 네트워크 드라이브·WSL 경로에서는 이벤트가 안 온다.
   - 권고: **A**. SPEC 원문이 "notify 등"이라 B도 허용 범위지만 B는 A의 상위집합이다. 나중에 지연이 문제가 되면 B를 "깨우기"로만 추가한다.

2. **합치기와 저장: 메모리만 vs SQLite 지금 도입**
   - (A) 메모리만: Rust 안에 세션·이벤트·중복 키 집합을 두고, 훅 이벤트와 로그 이벤트를 같은 곳에서 거른 뒤 프론트로 emit. 앱을 끄면 사라지고, 다음 시작 때 로그에서 다시 만든다(SPEC "DB는 지워도 로그에서 다시 만들 수 있어야" 와 같은 성질).
     최악: 훅으로만 받은 이벤트(로그에 안 남는 PermissionRequest·Notification 등, transcript를 끈 세션)는 재시작하면 사라진다. 로그가 큰 경우 메모리 사용이 커진다(질문 4의 상한으로 묶음). 시작할 때마다 전체를 다시 읽는다.
   - (B) 이번에 `orbit.db`(SQLite, 마이그레이션 0001, 유일 제약) 도입.
     최악: 새 의존성(rusqlite 등)과 마이그레이션·백업·버전 검사(SPEC "마이그레이션" 절 전체)가 이번 범위에 들어와 run이 두 배 가까이 커진다. 스키마를 ④ 화면 요구를 보기 전에 정하게 되어, 배포된 마이그레이션은 고칠 수 없다는 규칙 때문에 되돌리기 어렵다.
   - (C) 메모리 + 읽은 위치(오프셋)만 `app_data_dir`의 JSON 파일에 저장(시작 시 다시 읽지 않음).
     최악: 오프셋 뒤만 읽으면 과거 이벤트는 메모리에 없으므로 화면에 과거 세션이 안 나온다 → 결국 세션 요약도 저장해야 해 사실상 B의 일부를 손으로 만든다.
   - 권고: **A**. 합치는 위치는 Rust(한 곳에서 거르고 `cargo test`로 검증 가능). 프론트에서 합치면 중복 제거가 TS에만 있어 `cargo test`로 못 잡고 화면 새로고침마다 상태가 사라진다. DB는 SPEC의 저장 요구(비용 집계·run 기록)가 실제로 필요해지는 마일스톤에서 도입 — 어느 마일스톤인지 함께 정해 주기 바란다(Lead 제안: ④ 시작 전 별도 run).

3. **서브에이전트 로그(`<session>/subagents/agent-*.jsonl`)를 이번에 포함할지**
   - (A) 제외: 파일 선별에서 명시적으로 무시(테스트로 고정). 서브에이전트는 훅의 SubagentStart/SubagentStop으로만 보인다.
     최악: Orbit이 꺼져 있던 동안의 서브에이전트 안 도구 호출은 화면에 없다. 훅을 통해 들어온 서브에이전트의 도구 호출과 로그의 같은 호출을 합칠 기회가 없어, ④가 서브에이전트 노드를 그릴 때 과거 기록이 비어 있다. ④에서 다시 이 코드를 열어야 한다.
   - (B) 포함: 재귀로 읽고 경로상 부모 세션에 귀속(줄의 `sessionId`가 부모와 같음, 실측), `agentId`를 이벤트에 붙인다.
     최악: 줄 형식이 문서상 "같은 형식"이라는 말뿐이라 실측 표본 하나에 기댄 귀속 규칙이 틀릴 수 있다. 범위와 테스트가 늘어난다.
   - 권고: **A**(가장 작은 쪽). ④가 서브에이전트 노드를 그릴 때 포함한다.

4. **시작 시 과거 기록을 얼마나 거슬러 읽을지 (메모리 상한 포함)**
   - (A) 전부: 보이는 `<uuid>.jsonl`을 모두 처음부터 읽는다. 세션당 메모리에 두는 이벤트 수에 상한(예: 최근 500개)을 둔다.
     최악: 로그가 수백 MB면 시작 직후 수 초~수십 초 CPU·디스크를 쓴다(측정 안 함). 상한을 넘은 오래된 이벤트는 화면에 없다.
   - (B) 최근 수정 N일(예: 7일) 이내 파일만, 그 이전 세션은 목록에도 안 나온다.
     최악: SPEC 완료 기준 "Orbit을 나중에 켜도 과거 세션이 로그에서 복원된다"를 N일로 좁히는 것이 된다(Claude Code 기본 보관은 30일).
   - (C) 모든 파일을 세션 목록에는 올리되(파일명·수정 시각만), 내용은 최근 N일 파일만 읽는다.
     최악: 오래된 세션은 `cwd`·타임라인이 비어 보인다. 코드가 A·B보다 조금 늘어난다.
   - 권고: **A**(코드가 가장 작고 SPEC 완료 기준을 그대로 만족). 시작 비용이 문제로 드러나면 C로 옮긴다. 상한 값은 Architect가 PLAN에 적는다.

5. **`CLAUDE_CONFIG_DIR` 존중**
   - (A) 존중: 설정돼 있으면 `<CLAUDE_CONFIG_DIR>/projects`를 본다(릴리스 빌드에서도). 한두 줄.
     최악: Orbit을 띄운 환경과 Claude Code를 띄운 터미널의 환경변수가 다르면 엉뚱한 폴더를 본다. 이 경우 화면의 "감시 중인 폴더" 줄로만 알 수 있다. ②의 훅 설치 대상(`~/.claude/settings.json`)은 이 변수를 따르지 않아 두 기능이 다른 폴더를 볼 수 있다.
   - (B) 무시: 항상 `~/.claude/projects`.
     최악: `CLAUDE_CONFIG_DIR`을 쓰는 사용자는 세션이 하나도 안 보이고 이유도 모른다.
   - 권고: **A**. 단 ②의 설치 대상과 어긋나는 문제는 이번에 고치지 않고 후속으로 적는다(고칠지 함께 정해 주기 바란다).

6. **줄 길이 상한**
   - 사정: 줄에 시스템 프롬프트·도구 정의·`api-request-blob`이 들어가 매우 길 수 있다. 줄 길이 분포는 측정하지 않았다(RESEARCH).
   - 선택지: (A) 16 MiB. (B) 64 MiB. (C) 상한 없음.
   - 최악: A·B — 상한을 넘는 줄 안에 도구 호출이 있으면 그 호출이 로그 쪽에서 빠진다(훅이 있으면 훅으로는 보인다). C — 한 줄이 파일 끝까지 `\n` 없이 자라면 메모리를 무한히 쓴다.
   - 권고: **A**. QA가 이 PC의 실제 로그로 최대 줄 길이를 재는 것은 사용자 몫(14번과 함께)으로 두고, 넘는 줄이 흔하면 올린다.

7. **도구 호출이 아닌 사건의 중복**
   - 사정: 훅의 UserPromptSubmit·Stop 등은 `tool_use_id`가 없고, 로그의 사용자·어시스턴트 줄과 맞출 확인된 키가 없다(`prompt_id` ↔ `promptId`는 이름만 대응, 값 일치 미확인). 이번 범위는 타임라인에 도구 호출만 보이므로 이 줄들은 화면에 나오지 않는다.
   - 선택지: (A) 이번에는 도구 호출만 중복 제거하고 나머지는 화면에 안 낸다. (B) `prompt_id` 등 미확인 키로 맞추기 시도.
   - 최악: A — ④에서 프롬프트·턴 경계를 타임라인에 넣을 때 그때 다시 정해야 한다. B — 키가 실제로 다르면 같은 프롬프트가 두 번 보이고, 검증할 실측 데이터가 없다.
   - 권고: **A**.

8. **새 의존성**
   - 질문 1·2에서 A·A를 고르면 새 크레이트도 새 npm 패키지도 없다. 다른 선택을 하면 정확한 목록은 Architect가 PLAN에 적고 PLAN 승인 때 사용자가 본다.
